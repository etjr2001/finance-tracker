- ~~**Category uniqueness is case-sensitive in the backend.**~~ Done (`fix/category-name-case-insensitive`, `V4__category_name_case_insensitive_unique.sql`). `CategoryRepository`/`CategoryService` switched to `existsByUserIdAndNameIgnoreCase` (create) and `existsByUserIdAndNameIgnoreCaseAndIdNot` (rename — excludes the Category's own row, so renaming "Groceries" to "groceries" is a casing change, not a rejected collision with itself). - ~~**No pagination on `GET /api/transactions`.**~~ Dropped, not deferred (grilled 2026-09-26). Every list query is bounded to one month (ADR0011), search included, and one month's Transactions is a small list, so there's nothing to paginate. No safety cap on the month query either. Only comes back if search is ever widened beyond the selected month.
- ~~**No `created_at` on `transactions`.**~~ Done (`chore/transactions-created-at`, Recurring sprint item 2). `V7__transactions_created_at.sql` adds a nullable `created_at timestamptz`, defaulting to `now()` for new rows. Rows from before V7 stay `null`, meaning "created before this migration, time unknown", and a `comment on column` says so. Rejected: `not null default now()`, which stamps every old row with the migration's time, and a sentinel like epoch 0, which looks like real data to every query.
  - *Two statements, not one.* `add column ... default now()` would also stamp the old rows: Postgres evaluates a default given in ADD COLUMN once and fills existing rows with it. So the column is added bare, then `set default now()` follows, which only affects later inserts.
  - The `Transaction` entity leaves it unmapped. `ddl-auto: validate` ignores extra columns, and Hibernate's INSERT omits it, so the default fills it. Not in any API response.
  - Checked on local-dev 2026-11-15: old rows stayed `null`, and a new Transaction got a timestamp. `favourites` has had `created_at` since V6.
- **No DB-level `amount >= 0` check on `transactions`.** Only the entity's `@PositiveOrZero` enforces it. `favourites` has the check from the start (V6). Add `chk_transactions_amount_non_negative` `not valid`, check prod for negative rows, then validate it (same pattern as V2 and V5).
- **Entities expose public setters.** `Transaction`, `Category` and `Favourite` use Lombok `@Setter`, and services set fields one by one in both create and update, so each entity's field list is repeated. Replace with an `apply(...)` method per entity (or a constructor plus `apply`), drop `@Setter`, and update the services and test helpers (e.g. `CategoryServiceTest`'s `category(...)`). `Category` has no builder yet. Do all three in one refactor so they stay consistent.

It's in the base file, so prod and dev both get it. Backend tests don't open a database connection, so this was checked in the prod logs instead: the warning had stopped as of 2026-11-12.
