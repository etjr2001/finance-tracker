## Tech debt

- ~~**No backend test suite (pre-ADR0007).**~~ Resolved going forward, not backfilled all at once: the boilerplate smoke test deleted in sprint 1 was never replaced with an equivalent, but ADR0007 (tests land alongside whatever code is next touched) has since produced eight test classes — `GlobalExceptionHandlerTest`, `DashboardServiceTest`, `CategoryServiceTest`, `TransactionServiceTest`, `CategoryRequestValidationTest`, `TransactionRequestValidationTest`, `MonthParamTest`, `ResponseMappingTest`. See `src/test/java/com/project/financetracker/README.md` for the no-live-Supabase approach.
- ~~**Category uniqueness is case-sensitive in the backend.**~~ Done (`fix/category-name-case-insensitive`, `V4__category_name_case_insensitive_unique.sql`). `CategoryRepository`/`CategoryService` switched to `existsByUserIdAndNameIgnoreCase` (create) and `existsByUserIdAndNameIgnoreCaseAndIdNot` (rename — excludes the Category's own row, so renaming "Groceries" to "groceries" is a casing change, not a rejected collision with itself). Checked first: no existing case-duplicate names, so the migration needed no data cleanup. Replaced `uq_categories_user_name` with a unique index on `(user_id, upper(name))`, matching the `upper()` Spring Data's `IgnoreCase` generates.
  - **Merge order:** numbered `V4` because `V3` belongs to `feat/category-color-icon` (Sprint 3 item 1). `V3` merged to `main` first (#30), so this one is clear to follow it.
  - *Considered and rejected:* storing only uppercase names. It gives the same speed but throws away the casing the User typed.
- ~~**Inconsistent DTO usage.**~~ Done (`refactor/transaction-response-dto`, Sprint 3 Bundle A). `CategoryResponse` and `TransactionResponse` replace the entities the Category and Transaction endpoints used to serialize directly. Both drop `userId`; the JSON is otherwise unchanged, so the frontend and `demoApi.js` needed no edits. `DashboardResponse` already was a DTO.
- ~~**No pagination on `GET /api/transactions`.**~~ Dropped, not deferred (grilled 2026-09-26). Every list query is bounded to one month (ADR0011), search included, and one month's Transactions is a small list, so there's nothing to paginate. No safety cap on the month query either. Only comes back if search is ever widened beyond the selected month.
- **No `created_at` on `transactions`.** Nothing records when a Transaction was entered, only its `date`. Useful for debugging and for duplicate detection (Backlog). Add `created_at timestamptz` with `default now()`, **nullable**: existing rows stay `null`, meaning "created before this migration, unknown". Not `not null default now()`, which would stamp every old row with the migration's time, and not a sentinel like epoch 0, which looks like real data to every query. Add a `comment on column` saying what `null` means. Own branch after Favourites merges; the entity can leave it unmapped (`ddl-auto: validate` ignores extra columns). `favourites` gets `created_at` from the start (V6).
- **No DB-level `amount >= 0` check on `transactions`.** Only the entity's `@PositiveOrZero` enforces it. `favourites` has the check from the start (V6). Add `chk_transactions_amount_non_negative` `not valid`, check prod for negative rows, then validate it (same pattern as V2 and V5).
- **Entities expose public setters.** `Transaction`, `Category` and `Favourite` use Lombok `@Setter`, and services set fields one by one in both create and update, so each entity's field list is repeated. Replace with an `apply(...)` method per entity (or a constructor plus `apply`), drop `@Setter`, and update the services and test helpers (e.g. `CategoryServiceTest`'s `category(...)`). `Category` has no builder yet. Do all three in one refactor so they stay consistent.
- ~~**First request after an idle spell lags; Hikari logs "Failed to validate connection".**~~ Fixed on `feat/favourites` (a small config change, so not its own branch). Supabase's Session pooler drops idle connections, but Hikari kept them for its 30-minute default `max-lifetime`, so the first query after a quiet spell hit a dead connection and had to reconnect. `application.yml` now sets `spring.datasource.hikari`: `max-lifetime` 5 min, `keepalive-time` 2 min, `idle-timeout` 4 min, `minimum-idle` 2, `maximum-pool-size` 5 (the pooler caps client connections). It's in the base file, so prod and dev both get it. Backend tests don't open a database connection, so this was checked in the prod logs instead: the warning had stopped as of 2026-11-12.
- **`frontend/test` doesn't mirror `frontend/src`.** #29 moved `src` into `features/<feature>/{api,components,hooks,pages,utils}` but left `test/` in the old flat layout: `components/`, `hooks/` and `pages/` mix shared and feature files, `lib/` holds what `src` now calls `utils`, and only `demo/` is grouped by feature. Move the tests so each one's path mirrors its source file's (e.g. `test/features/favourites/hooks/useFavourites.test.jsx`, `test/utils/date.test.js`), and rename `lib/` to match. Moves only, no test changes, on its own `refactor/` branch after Favourites merges. Started on `feat/favourites`: the tests that branch added or edited already live under `test/features/` (`demo`, `favourites`, `layout`), so the refactor only moves the rest. New or edited tests go at the mirrored path from now on, which leaves `test/demo/` holding only `demoMoney.test.js` until then. Colocating tests next to source was the other option, but it contradicts "tests in `frontend/test/`" (CLAUDE.md) and would need an ADR.
- **No custom domain/DNS.** The app is live on the default Railway URL. Explicitly non-blocking, parked indefinitely.
- ~~**Bottom tab bar feels too narrow to tap comfortably on phone.**~~ Fixed (`fix/nav-bar-tap-targets-and-new-transaction-date`): grew the `NavLink`s from `min-h-11`/`py-1.5` to `min-h-14`/`py-2`, so the tap targets themselves sit clear of the iPhone home-indicator gesture area — the existing `pb-[env(safe-area-inset-bottom)]` only cleared the bar's *background* there, not the tappable zone. Awaiting on-device confirmation this was the whole story. Later found (UI transitions, below) that `env(safe-area-inset-bottom)` is always 0 here: `index.html` has no `viewport-fit=cover`, so iOS keeps the page out of the unsafe area itself. The tab bar now floors its bottom padding at 0.375rem. Adding `viewport-fit=cover` would make the safe-area padding real, but extends the whole layout under the notch and home bar, so it's its own change.

- ~~**Page behind an open Modal/Sheet stays reachable by keyboard and screen readers.**~~ Done (`feat/dialog-motion-and-focus`). `Modal` and `Sheet` portal into `<body>`. `useEscapeKey`'s stack became `useLayer` (`src/hooks`): while a modal layer is open, every other `<body>` child is `inert` (the app root, and a modal under a stacked one); focus moves into the dialog and back to the opener on close. A layer leaves the stack as soon as it starts animating out, so a quick second Escape reaches the layer below. Backdrop clicks now count only on the backdrop itself, since React events bubble through portals. The `openCreate`/`openEdit` "form already open" guards are gone.
- ~~**Page behind an open Modal/Sheet still scrolls.**~~ Done (same branch): `useLayer` sets `overflow: hidden` on `<html>` and `<body>` while any modal layer is open, counted across stacked ones. Confirmed on a real iPhone 2026-11-12.
- ~~**Reduce Motion turns off every animation, not just movement.**~~ Done (same branch), as decided 2026-11-09: under reduced motion, fades stay and movement goes. `ExitPresence` keeps exits; Modal, Sheet and the month popover fade instead of popping or sliding (a swipe still follows the finger, then fades); backdrops and Card always fade; the segmented-control thumb jumps but its colours fade; the nav highlight crossfades. `useReducedMotion` covers Sheet's JS-driven slide.
- ~~**Month bar: "This month" too small to tap, and month changes look out of sync.**~~ Done (`fix/month-bar-tap-and-loading`).
  - *Tap target.* Below `sm:` `ThisMonthButton` (`MonthBar.jsx`) was a 14px icon with no padding, about 14×20px. A full 44px-wide button pushed Add off narrow phones, so the button is now `h-11 w-7` and a `::before` widens the hit area 8px each side to 44×44. 8px is the bar's `gap-2`, so it never overlaps the Next arrow. To pay for the extra width, the month label's min width is `min-w-32` below `sm:` (still fits "September 2026") and `min-w-36` from `sm:` up. Confirmed on a phone 2026-11-12. Not `IconButton`, which has no slot for the `sm:`+ text.
  - *Loading on month change.* `useDashboard` now has `keepPreviousData` like `useTransactions`. Both pages wrap their content in `StaleContent` (`src/components`), which dims it to 50% and sets `aria-busy` while `isPlaceholderData`, so stale data never looks current. "Loading…" only shows on the first load. `usePrefetchAdjacentMonths` (`src/hooks`) prefetches the months either side, with a 60s `staleTime` so a neighbour that was just loaded isn't fetched again. Each hook builds its query options once for both `useQuery` and the prefetch. The cache keeps React Query's default 5-minute `gcTime` (decided 2026-11-12): memory only, so at most the viewed month plus 2 neighbours per page are in use.
  - *Dev-server gotcha found on the way.* `usePrefetchAdjacentMonths` uses React 19's `useEffectEvent`. A stale Vite dep cache (`node_modules/.vite`) served an older React, which showed as "Should have a queue" and then a blank page, while every test passed. `npx vite --force` fixed it. Prod builds from scratch, so it isn't affected.
- ~~**Logout leaves the previous User's data in the cache.**~~ Fixed on the same branch, found 2026-11-12. Query keys aren't scoped by User, and logout only signed out of Supabase, so the next User to log in on the same tab within the 5-minute `gcTime` could briefly see the previous User's Transactions and Dashboard. `AuthProvider` now calls `queryClient.clear()` on Supabase's `SIGNED_OUT` event, which covers a manual logout, an expired session, and a sign-out in another tab. It also clears when a different User signs in over the current session (a signed-in tab going straight to `/login`), which Supabase reports as `SIGNED_IN` only. The same User signing in again keeps the cache. A crash or a closed tab needs nothing, since the cache is memory-only.
- ~~**A crash shows React Router's bare "Unexpected Application Error" page.**~~ Fixed on the same branch. No route had an `errorElement`. `RouteError` (`features/layout/components`) is now the `errorElement` on each page route, where it renders inside `AppLayout` so the nav stays, with a Reload button. A full-page version on the root route catches layout, auth-page and `AuthProvider` crashes and adds Go to Dashboard (`/demo` in demo mode), which does a full page load. The error message shows only in development.

- ~~**A zero-amount Draft shows "−$0.00" in the Transactions list.**~~ Fixed on `feat/field-help-icon`, found 2026-11-14. `SignedAmount` signed every amount by type, so an Expense Draft showed "−$0.00" (an Income Draft "+$0.00") next to a "$0.00" day total, which `formatMoney` already keeps unsigned. A zero amount now gets no sign; colour still follows the type. Not a change to ADR0010, which only fixes the glyph (U+2212) for signed amounts. Showing "No amount" instead, like Favourites, was considered and rejected (decided 2026-11-14: keep "$0.00").
- **Form labels use two colours.** `FormField` labels are `text-ink`: Note on both forms, the Category name inputs (`NewCategoryModal`, `CategoryEditModal`), and Email/Password on the auth pages. `AmountField`, `CategorySelect` and `DateField` pass `text-ink-soft`, so the Transaction and Favourite forms mix both. Accidental, not decided: every Transaction form label started as `text-ink-soft` (`9ec6ac2`), then #18 created `FormField` with a plain `text-sm` label, so Note and "New category name" turned ink when they moved onto it, while Amount, Date and Category stayed hand-written and soft. ADR0010 has no label-colour rule (`ink-soft` is "secondary text"). All now go through `FieldLabel`, so the fix is one class. Pick one, checking ADR0010 first.
- **Demo mode: "Exit demo" starts off screen in the desktop sidebar.** Found 2026-11-14. `Sidebar` is `md:sticky md:top-0 md:h-screen` with Exit at the bottom (`justify-between`). In demo mode `DemoBanner` (also `sticky top-0`) sits above it, so on load the sidebar starts below the banner and its bottom, with "Exit demo", is off screen by the banner's height. Once scrolled, the banner covers the top of the sidebar ("Ledger") instead. Logged-in mode has no banner, so it's fine. Fix options: put the banner and sidebar in one sticky region so the sidebar's height accounts for the banner; offset the sidebar by the banner's measured height; or move Exit up under the nav. Own `fix/` branch. Mobile is a separate, smaller matter: `MobileHeader` (and its Exit/Log out icon) isn't sticky, so it scrolls away in both modes.
- **`useTransactionEditor` and `useFavouriteEditor` duplicate most of their logic.** Form open/close, the unsaved-changes check, the delete confirm and the error line are near-identical; only the mutations, messages and Transactions' month jump differ. The detail card is already shared (`useDetailCard`). A shared editor hook taking the mutations and messages would remove the rest; both hooks have page tests, and `useFavouriteEditor` its own. Not urgent.

### Pre-Sprint-3 hardening: complete
Not a numbered sprint — a batch of bug fixes and tech debt cleanup found ahead of Sprint 3, shipped as independent branches:

- **Request validation gaps (#6).** `amount` capped to fit `numeric(12,2)` (±9,999,999,999.99), `note` capped to 256 chars, category `name` to 50 (later tightened to 30, Sprint 3 item 1) — matched on frontend and backend. DB-level `CHECK` constraints added `NOT VALID` (`V2__note_and_name_length_checks.sql`) so the migration couldn't fail on existing over-length rows.
  - ~~**Prod check for existing over-length `note`/`name` values.**~~ Done (2026-09-30): no rows over 256 chars (`note`) or 30 chars (Category `name`) in prod. `V5__validate_note_and_name_length_checks.sql` validates both constraints. The category case-insensitivity fix above already ran its own prod check (no existing case-duplicate names found) — this was the separate, `note`/`name` length check.
- **Raw DB error leaked to the frontend + no backend logging (#7).** `GlobalExceptionHandler.handleDataIntegrityViolation` no longer returns `ex.getMessage()` (raw Postgres/Hibernate text) to the client — generic message instead, real exception logged server-side. Every handler now logs via SLF4J, where previously none did, including the catch-all. Added `GlobalExceptionHandlerTest` covering every handler, closing the tech-debt item from #4 where this file was changed without a test.
- **Date input rendering wider/taller than other fields on iOS Safari (#8, #9).** Root cause was iOS's native `<input type="date">` rendering, not generic browser chrome — confirmed only reproducible on real Safari, not Chrome's mobile device emulation (which still renders form controls with Blink, not WebKit). First attempt (`min-w-0`/`h-10`) didn't fix it; the working fix was `appearance-none`/`-webkit-appearance:none` on the date input, same technique already used for the Category select.
- **JWT lost on every iOS home-screen relaunch (#10).** Not a Supabase config issue — iOS home-screen bookmarks added without a Web App Manifest don't reliably persist `localStorage` across relaunches. Added a minimal `manifest.json` (name, icons, `display: standalone`, `start_url`) plus `apple-touch-icon`/`apple-mobile-web-app-capable` meta tags. No service worker, no offline support — scoped purely to fix storage persistence, not to make the app an installable PWA (see backlog item above). Also replaced `favicon.svg` (previously a generic purple/blue mark that didn't match the app's palette) with a design in the app's actual colors, and fixed `index.html`'s `<title>` (was the default Vite placeholder).
- **Mobile form UX (`fix/mobile-form-ux`).** Found while testing #10 on a real device, not part of the original five bugs: `TransactionForm` now stacks one field per line on mobile and two on web; the amount field blocks a keystroke that would exceed `numeric(12,2)`'s range instead of only warning on submit, with an inline hint so the block doesn't look like broken input; and `TransactionForm`/`CategoriesPage` inputs moved from `text-sm` (14px) to `text-base` (16px), since iOS Safari auto-zooms the viewport on focus for any input under 16px and doesn't reliably zoom back out.
- **Frontend-only `/demo` mode (#12).** Every route behind `ProtectedRoute` meant a cold visitor hit a signup wall before seeing anything work. `/demo` (ADR0009) renders the real Dashboard/Transactions/Categories UI against browser-local state (`frontend/src/features/demo/`) — no backend or Supabase calls — and is now the default landing page for a logged-out visitor. Same PR closed a validation gap found while building it: `TransactionForm`'s amount field blocked exceeding the `numeric(12,2)` max but not extra decimal places, which the backend already rejected via `@Digits(fraction = 2)` but the demo (with no backend to catch it) didn't guard against at all.
- **Dashboard breakdown included Drafts (#13).** `DashboardService.buildCategoryBreakdown` didn't actually exclude zero-amount Transactions, despite ADR0008 documenting that as the decision — surfaced because `/demo` mode's client-side dashboard implemented the correct behavior, so the real app started visibly disagreeing with its own demo. Fixed, with `DashboardServiceTest`, the first backend service-layer test in the repo.

1. ~~**Category color/icon.**~~ Done (`feat/category-color-icon`). Built as designed (grilled — a DB-backed lookup table with FK-validated keys was considered and rejected: it would need a synced-but-duplicate frontend registry anyway, since ADR0010 requires code-based colour tokens and explicitly-imported icons for tree-shaking, for no real integrity benefit in a single-developer, low-write table), with a few deviations found along the way:

Creating from the Categories page *does* auto-assign: colour is a deterministic hash of the name, icon is a keyword guess (reusing the same keyword list the old name-guess stopgap used) that falls back to unset (not a wrong guess) when nothing matches. ### Favourites and Recurring: in progress
Brought forward ahead of Sprint 4 so the app can show how much of the month bills have already spoken for. Two phases, each on its own branch; Phase 2 starts after Phase 1 merges. Favourite and Recurring stay two terms and two tables (ADR0017).

1. **Phase 1: Favourites (`feat/favourites`, ADR0017).** Done (#46).

   - Frontend: a Favourites nav tab for adding, editing and deleting; a Favourites button in the Add transaction form, opening an A–Z list that fills the form in place; and a star on each Transaction (row actions on desktop, the bottom-sheet detail card on mobile), outline or filled by whether it matches a Favourite, which opens Add or Edit favourite in place over the Transactions list.
   - Editing was first left out, then brought into this phase (2026-10-18).
2. **Phase 2: Recurring (`feat/recurring`).** Settled (grilled 2026-10-11, details 2026-11-11), not started. Next: write ADR0018 and the `CONTEXT.md` entry, then build.
   - Its own table and a Recurring page (fifth nav item, after Favourites; check the bottom tab bar still fits on a phone). Created from scratch or with "Make recurring" on a Transaction. Only the job links a Transaction to a Recurring item.
   - Schedule: a frequency (every N days, weeks, months or years) with two fixed anchors, one for when the entry is posted and one for the date the Transaction gets (e.g. posted on the 1st, dated the 21st). Editing either date re-anchors from the new dates; entries already posted stay as they are.
   - "Amount varies" posts Drafts (amount zero). ADR0008 is unchanged.
   - Runs as a scheduled job in the same Railway instance (ADR0001), plus a catch-up run at startup, so runs missed during a redeploy or while the app slept are posted with their correct dates. Assumes a single replica; a version column guards against double-posting.
   - "Left to avoid spending: $X + N unknown" next to the Drafts notice: Expense entries still to come this month, plus a count of varying-amount ones.
   - Details settled 2026-11-11:
     - *Month end.* Dates clamp to the month's last day, always computed from the original anchors (31st → Feb 28/29 → Mar 31; a yearly Feb 29 → Feb 28 in non-leap years), so they never drift.
     - *First run.* The start date must be today or later; nothing is ever posted into the past. "Make recurring" on a Transaction defaults to the next cycle after its date. Backfilling past runs is left to the clone action (Backlog).
     - *Stopping.* Stop (sets an end date; the item stays listed with "until") or Delete. Transactions already posted always stay (`recurring_id` set to null on delete). No pause/resume in v1 (Backlog).
     - *Future-dated Transactions.* Intended ("spoken for"): shown in the list and counted on the Dashboard. The Transaction date is never before the post date.
     - *Category delete guard.* Also blocked while a Recurring item uses the Category, like Favourites.
     - *Demo (ADR0009).* Posting is mirrored in `demoApi.js` through one shared schedule util, tested against the same cases as the Java schedule tests.
     - *"Left to avoid spending".* Current month only (hidden for other months). Expenses only. $X = Recurring Expenses dated after today this month, posted or not; N = varying-amount items with an occurrence still to come this month.
     - *Catch-up.* Every missed run is posted with its correct date, capped at 366 runs per item per pass; anything past the cap is logged and posted on the next pass.

### UI transitions: complete (#47)
A short polish pass between Favourites (Phase 1) and Recurring (Phase 2), on `feat/nav-active-state-and-page-transitions`. Frontend only, no API changes. Motion rule throughout: no content blending or sliding (a crossfade between pages caused motion sickness and was dropped); only small elements move, content only fades in; everything is off under `prefers-reduced-motion`.

- **Router.** `App.jsx` exports `routes` for `createBrowserRouter` (`main.jsx`), with `AuthProvider` as a layout route. Routes must be registered with the data router itself: React Router drops NavLink's `viewTransition` for links under a nested `<Routes>`. `test/App.test.jsx` guards this.
- **Nav.** The active nav item gets a filled `deposit` highlight (full cell in the tab bar, a rounded fill in the sidebar) that slides to the new item via a View Transition; pages themselves swap instantly. The tab bar has 0.375rem padding above and below its labels. Its bottom padding never actually used the safe-area inset: `index.html` has no `viewport-fit=cover`, so iOS reports the inset as 0 (see the tab bar item in Tech debt).
- **Month picker.** Desktop dropdown is left-aligned with the month bar; "Choose month" is centred. On mobile it opens in the shared `Sheet` instead of its own hand-built bottom card.
- **Popups.** `ExitPresence` (`src/components`) keeps a closed popup on screen for 200ms so it can animate out; every conditional Modal/Sheet/popover is wrapped in it. `Modal` fades and pops in and out; `Sheet` slides up and down on mobile (from wherever a swipe let go) and pops on desktop. `Modal` also gained `role="dialog"`/`aria-modal`.
- **Cards.** `Card` fades in on mount, so a new month's cards fade in rather than blink. Also fades cards on page switches; if that's too much, fall back to fading only on month change.
- **Add button.** Transactions and Favourites share `PageToolbar`; Add no longer hides while its form is open (hiding it shifted the Favourites list). `openCreate`/`openEdit` are no-ops while a form is open (see the inert item in Tech debt).
- **Segmented control.** The Expense/Income thumb now slides on iPhone Safari: it used `left: calc(% + px)`, which WebKit won't animate; now a plain-percentage `translateX`. Confirmed on iPhone 2026-11-12. Under Reduce Motion it jumps instead of sliding, which is intended, and the user chose to keep it.

All device checks were confirmed 2026-11-12, including the Card fade on page switches, which is fine as is. Follow-ups found during review are in Tech debt (Reduce Motion fades, month bar, background scroll).
